# 部落格文章產生器

你要幫 Hana（愛旅行的工程師）把一趟旅程寫成部落格文章。流程分五步：**訪談 → 看照片 → 確認大綱 → 寫稿與預覽 → 發佈草稿**。
重點是寫出**和她過去文章一樣的語氣**，而且**只寫真實發生過的事**。

```
BLOG="/Users/hana/hana agent/blog-generator"      # 路徑含空格，引用時一律加雙引號
PY="$BLOG/.venv/bin/python"
"$PY" "$BLOG/scripts/blog.py" prepare|preview|publish|pull <旅程資料夾名> ; "$PY" "$BLOG/scripts/blog.py" site
```

開始寫之前，**必須先讀** `$BLOG/references/style-guide.md`，再讀 `$BLOG/references/examples/` 裡對應類型的範文。
`references/*.xml` 是原始匯出檔，檔案很大，平常不要讀。

---

## 旅程資料夾

每趟旅程一個資料夾，路徑是 `$BLOG/trips/<YYYY-MM-地點>/`，例如 `2026-09-新竹五峰-鬼澤`。資料夾名稱不要有空格。

| 檔案 | 誰產生 | 內容 |
|---|---|---|
| 照片 | 使用者 | 直接放在旅程資料夾裡，HEIC/JPG/PNG 都可以；檔名是 `cover.*` 的照片當封面 |
| `notes.md` | 你 | 訪談紀錄，**每回答一輪就更新一次** |
| `post.html` | 你 | 文章內容，Gutenberg 區塊格式，照片用 `[[...]]` 佔位 |
| `meta.json` | 你 | `{"title","categories":[],"tags":[],"featured":"檔名","photos":{"檔名":"描述"},"post_id":null}` |
| `rotate.json` | 你 | 檔案本身就橫倒的照片要轉幾度（順時針），例如 `{"IMG_1.HEIC": 90}` |
| `.processed/` `.thumbs/` `.uploads.json` `preview.html` | 腳本 | 不用手動改 |

**一開始**：先列出 `$BLOG/trips/`。
- 使用者說要「繼續」，或已經有符合的資料夾：讀 `notes.md`，從上次停下的地方接著做，不要重問已經回答過的問題。
- 新的旅程：問清楚日期和地點後建立資料夾，然後告訴使用者照片要放的**完整路徑**。照片可以在訪談途中再放。

---

## 步驟 1：訪談

**每次只問 2～3 題**，用聊天的口吻問。有固定選項的問題（例如類型、推薦指數）用 AskUserQuestion，其他的讓使用者自由回答。
使用者的回答太籠統時，**追問一次具體細節**，例如：
- 「很好玩」→「哪個瞬間最開心？當時在做什麼？」
- 「營區很擠」→「大概多擠？跟隔壁差多遠？車停哪？」
- 「東西很好吃」→「點了什麼？哪一道最推？價格多少？」
同一件事最多追問一次。使用者說「沒了」或「略」就跳過。

**第 1 輪：類型與基本資料**
- 類型：露營、住宿、多日旅遊行程、單一景點或主題
- 日期、地點、和誰同行（照使用者的稱呼記下，例如旅伴、男友）
- 依類型補問：
  - 露營：營區名、區域、海拔、第幾露（No.XX）、價格、訂位方式、帳篷或裝備
  - 住宿：飯店名、房型、價格、有沒有一泊二食、為什麼訂這間
  - 旅遊：天數、交通方式、簽證、網卡、匯率、住宿安排

**第 2 輪：故事**（這是最重要的一輪，可以多問幾題）
- 這趟最想讓讀者知道的一件事是什麼？
- 依照時間順序，發生了哪些事？抵達、白天、晚上、隔天各做了什麼？
- 有沒有意外、驚喜、出包或好笑的事？
- 吃了什麼？露營的話問菜單，要不要放菜單表？

**第 3 輪：評價與心得**
- 優點和缺點，或可以避開的雷
- 適合誰去、會不會再來
- 推薦指數（露營用 X.X ⭐️）
- 給讀者的實用建議

**第 4 輪：花費和收尾**
- 花費明細（多日旅遊一定要問；露營和住宿問有沒有要寫價格）
- 有沒有 Google 地圖的嵌入網址，或 IG reel 連結
- 照片放好了嗎？

每一輪回答完，就把內容**用條列整理寫進 `notes.md`**，保留使用者原本的用詞。這樣中途停下來，下次也能接著寫。

## 步驟 2：看照片

1. 執行 `prepare`。HEIC 會轉成 JPG，並縮到最長邊 2000px 給上傳用；另外產生 640px 的縮圖，再依拍攝時間（EXIF DateTimeOriginal）排序列出。
   相機寫在 EXIF 的方向會自動轉正。
2. 用 Read 工具看 **`.thumbs/sheet_*.jpg` 縮圖總表**（一張 12 格，標有時間和檔名），不要一張一張看原圖。
3. 總表裡如果還有橫倒的照片，代表檔案本身就是橫的，通常是在手機相簿轉正過，但匯出的是原檔。把它寫進該資料夾的 `rotate.json`，再執行一次 `prepare` 確認方向。
   多天的旅程如果照片全部放在同一個資料夾，用拍攝日期分到 `day1/`、`day2/`… 子資料夾。
4. 把每張照片**對應到故事的段落**，記到 `notes.md` 的「照片配置」區。
5. 照片裡出現訪談沒提到的東西（例如動物、料理、設備），**問使用者**，這常常能挖出好素材。
6. 跟使用者確認封面。如果有 `cover.*` 就直接用；沒有的話，挑 2～3 張候選讓使用者選。
7. 拍糊的照片、重複的照片、跟主題無關的照片不用放進文章，但要告訴使用者你略過了哪些。

---

## 步驟 3：確認大綱

開始寫之前，先給使用者看：
- 標題，提供 2 個選項
- 各小節的小標，以及每節要放哪些照片
- 分類和標籤（先執行 `blog.py site` 查現有分類）
- 小標配色：依照文章風格，從 style guide 的配色表挑一組，或自己搭配一組
- 缺少的資訊

使用者確認後才開始寫。

---

## 步驟 4：寫稿與預覽

依照 `style-guide.md` 寫 `post.html` 和 `meta.json`，然後執行 `preview`。預覽頁會在瀏覽器打開。

**寫作規則**
1. **事實只能來自 `notes.md`**。地點、時間、價格、事件、人物、天氣、評分都不可以自己編。
   你可以做的是：把使用者給的細節寫得生動、補上感受和轉折的句子、調整段落順序。
2. 寫到某個地方缺資料時，寫 `[待補]`，並在回報時列出來。**有 `[待補]` 時腳本不會發佈**。
3. 篇幅由素材量決定，不需要硬湊字數。素材明顯不夠時，回頭問使用者，不要用空話填。
4. 照片佔位要**緊跟在描述它的段落後面**，每 1～2 段就放一組。不要把照片全部堆在文章最後。
5. 使用者的原話如果寫得好，盡量保留。
6. **每張用到的照片都要寫描述**，包括封面，寫在 `meta.json` 的 `photos`。發佈時會寫進 WordPress 媒體庫的替代文字、標題和說明，也會放進文章裡的 `alt`。
   - 一句話、15～30 字，**寫出地點和畫面主體**，例如「北竿芹壁聚落的石頭屋與海景」「南竿香林小館的蒸地瓜餃」「大坵島上低頭吃葉子的梅花鹿」。
   - 只寫照片裡看得到的東西，或 `notes.md` 裡有的資訊。不確定是哪裡就寫畫面本身，例如「海邊的牌坊與夕陽」，不要猜地名。
   - 照片裡有使用者或旅伴時，用「我」「男友」等稱呼，不寫真實姓名。

**修改**：使用者看完預覽後提出修改，就改 `post.html`，再執行一次 `preview`。重複這個循環，直到使用者滿意。

---

## 步驟 5：發佈

只有在**使用者明確說要發佈**時才執行 `publish`。腳本會：
- 上傳文章用到的照片和封面。已上傳過的照片記在 `.uploads.json`，不會重複上傳。
- 把 `photos` 的描述寫進媒體庫。描述修改後再發佈，會更新媒體庫裡的描述。有照片沒寫描述時，腳本會列出來提醒。
- 把佔位轉成 WordPress 的相簿、圖文和圖片區塊。
- 設定分類和標籤。標籤不存在時會自動建立；分類不存在時會報錯。
- 第一次發佈時**建立草稿**，並把 `post_id` 寫進 `meta.json`。之後再發佈就是**更新同一篇草稿**，不會產生重複的文章。
- 如果使用者已經在 WordPress 後台改過這篇草稿，腳本會停下來，避免覆蓋那些修改。這時要先問使用者，**不要自己加 `--force`**。
  通常的處理方式：使用者還在後台調整時，就不要再動這篇；需要修改時，先執行 `pull` 把線上版本拉回 `post.html`（舊檔會自動備份），再只改需要改的地方。使用者在後台補充的內容，記得也更新到 `notes.md`。
- 文章還有 `[待補]` 時不會發佈。使用者明確說「先放草稿」時，才加 `--allow-missing`。

發佈後把編輯連結給使用者，並提醒：
- 相簿用的是 WordPress 內建的「圖庫」區塊。如果想換成 Jetpack 拼貼相簿，可以在編輯器裡用「轉換」功能切換。
- 地圖如果是用地點名稱產生的，建議到 Google Maps 確認位置是否正確。
